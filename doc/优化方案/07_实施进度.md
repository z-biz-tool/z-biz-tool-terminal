  - `clipboard-manager:default` 的授权集是**空**（插件明说剪贴板默认不开），而 `SftpPanel` 复制路径调 `writeText` → 每次必然抛错、静默回退到 `navigator.clipboard`。现已显式授予 `clipboard-manager:allow-write-text`。

  - `shell:default` 只有 `allow-open`，且 `open()` 要先过正则 `^((mailto:\w+)|(tel:\w+)|(https?://\w+)).+` → 设置页"打开配置目录"传的 `~/.z-terminal` 必然被拒（且 `~` 本来也不会展开）。现改走 `open_file_with_default_app` + 绝对路径。
- **`open_file_with_default_app` 在 Windows 上二次过 shell**：`cmd /c start <path>` 会把路径里的 `&`、引号再解析一次；换成 `explorer.exe <path>` 单参数传递。
- **远程输出截断会 panic 在 UTF-8 中间**：`collect_channel_output` 原按字节下标 `&chunk[..remaining]` 卡 2 MB 上限，而远程日志常见中文（3 字节/字），下标落在字符中间会在 SSH 读任务里直接 panic 掉整条会话 —— 新增 `append_capped` 把截断点回退到字符边界，并补 1 例单测（`汉字测试` 在 limit 5/4 下分别保留 `ab汉` / `ab`，且结果必须 `is_char_boundary`）。
- **审计测试与配置测试抢同一个进程级环境变量**：`audit.rs` 的测试切 `Z_TERMINAL_CONFIG_DIR` 时，`config.rs` 的落盘测试会读到别人的目录（真实红过一次：`config.json 应存在: NotFound` + 2 个 `PoisonError` 级联）。现改为 crate 级共用一把 `CONFIG_DIR_TEST_GUARD` 串行锁（`config::lock_config_dir_env()`），panic 时取 `into_inner()` 而不把 panic 外溢成其它测试的毒化失败。
- **`ptyBus` 监听起来失败会把 rejected promise 永久留在模块里**：一次 `listen()` 失败后，后续所有订阅都建立在同一个已拒绝的 promise 上、永久失败。现失败即清空 `starting` 并抛出，下次订阅可重试。

## 7.11 阶段五第四轮：快捷键单一真源（顺带修掉两处真实缺陷）

起因是"查看快捷键"面板和 App.tsx 的 if 链是两份事实。逐条对照后面板说谎的地方比想象的多：

## 7.12 阶段五第五轮：分屏面板键盘聚焦（顺带修掉一处"分屏键冷启动就死"）

## 7.13 阶段五第六轮：顺着 stale-closure 把 `[]` 依赖 effect 全过一遍

## 7.14 阶段五第七轮：把"当前活动会话"抽成单一 helper（端口转发整页原本是死的）

上一轮埋的那处是真的功能缺失，不是风格问题：`tabs` 里 `id` 与 `serverId` 是两个命名空间，`t.serverId === activeTabId` 几乎不可能成立 —— 于是 `getSessionId()` 恒为 `undefined`，转发列表 / 新增 / 删除 / 诊断全部走进"没有活动的SSH会话"分支。用户视角是"这个面板从来不工作"。

根因不在那一行，而在**同一段查找被抄了多份**：抄的人改错了比较对象，另一份仍是对的，所以缺陷只在其中一个页面出现、审查时也容易看漏。因此这轮不是补一个 `id` 就交差，而是：

- 新增 `src/utils/session.ts` 的 `pickActiveSession(state)`：按 `activeTabId` 找标签，再按 `activePaneId` 找面板，取 `pane?.sessionId || tab.sessionId`；找不到标签返回 `undefined`。`activePaneId` 过期（面板已关）时回落到标签主面板，所以不会出现"因为一个脏 id 而全盘不可用"。

## 7.15 阶段五第八轮：端口转发的真源挪到后端（"面板以为在跑"≠"会话里在跑"）

先做了一次 IPC 契约对账：把 `src/` 里 47 个 `invoke("cmd", {…})` 的命令名与参数键，逐个对到 `src-tauri/src/lib.rs` 的 `generate_handler!` 与 `#[tauri::command]` 形参上（自己写的解析器踩了两个坑：嵌套泛型 `invoke<Partial<X>|null>('cmd')` 会被截断、对象简写的**值**会被当成键 —— 第一版因此报了 27 条假失配）。结论是命令名与参数键**全部对得上**，没有第二处"端口转发式的哑口"。但顺手读到 `PortForwardModal.refreshForwards()` 的函数体只有两行英文注释：`Currently we track forwards in component state only / In the future, we could invoke a command to list active forwards from backend`。这条不是笔误，是**整块功能没有真源**。

缺陷形状：转发进程活在 SSH 会话里（`SshSession.forwards`），面板却把"哪些在跑"记在自己的 `useState` 里。于是

- 切到另一个面板（另一个 sessionId）再开面板，列表仍显示上一个会话的转发；点"停止"就把 A 会话的 `forward_id` 发给 B 会话 —— 后端回"转发任务 f-1 不存在"，用户看到的是"我停不掉它"；
- 后端 accept 循环出错自己摘掉转发之后，前端那行永远留在表上（幽灵行）；
- 反过来，会话里确实在跑的转发，只要不是这个组件实例起的，就一条也看不见。

处理（一次改动的边界：只挪真源，不碰转发实现）：

- 后端 `SshSession.forwards` 的值类型从 `JoinHandle` 换成 `ForwardTask { join, spec }`，`ForwardSpec { kind, listen_addr, listen_port, target_addr, target_port }` 在三个 `start_*_forward` 里就地记下已解析好的监听/目标侧（刻意放在后端：前端 -R 那两个字段是反着塞的，只有这里名字和值才对得上）。**一张表管两样东西**，任务自我清理时 `remove(&fid)` 顺手带走描述，不留第二份会漂移的登记。
- 新增 `ssh_list_forwards(session_id)` → `{ success, forwards[], error }`，每行带 `alive`（`!join.is_finished()`）；`disconnect()` 与 `stop_forward()` 改为 `task.join.abort()`，语义不变。
- 前端 `refreshForwards()` 真的去读；三条启动口和停止口不再本地 append，改成 `await refreshForwards()`；无 sessionId 时清空而不是保留旧数据。列表区不再以"有没有行"为条件渲染 —— 空表要让用户看见"这个会话确实没有转发"，而不是"这个面板没读会话"。
- 展示文案抽成 `src/utils/forwards.ts` 的 `describeForward()`，统一"监听侧 → 目标侧"并点明哪一侧是本机（`本机 127.0.0.1:5501 → 远端 db.internal:5432` / `远端 0.0.0.0:2222 → 本机 127.0.0.1:80` / `本机 127.0.0.1:1080 (SOCKS5)`）；`parseForwardList()` 对读不懂的行**丢掉不补 0**，因为一条指向 `:0` 的假行会让人以为端口已经关了。
- 顺带：类型标签 `remote` 改成中文"远程"（同一张表里只有它没翻）。

`tests/forwards.test.ts` 36 例（`npm test` → **15 文件 / 481 例**），后端 `cargo test --lib` **73 passed**（+2：`forward_info_serializes_with_the_keys_frontend_reads`、`dynamic_forward_keeps_target_absent`）。最有价值的一组是**跨语言契约**：从 `commands.rs`/`ssh.rs` 里正则抽出 `ForwardInfo`+`ForwardSpec` 的字段名，snake→camel 之后要求 (1) 正好等于 wire 上那 7 个键，(2) `forwards.ts` 里 `item.X` 与解构出来的每个 `X` 都必须在这 7 个键里 —— 任何一侧改名都会当场红。另有静态守卫：面板必须调 `ssh_list_forwards`、必须 `setActiveForwards(parseForwardList(...))`、**不得**再出现 `setActiveForwards((prev) => [...prev, …])`、命令必须在 `lib.rs` 注册。

## 7.16 阶段五第九轮：字号/字体改完必须重新量几何（"改了字号"≠"改了 cols×rows"）

缺陷形状：`TerminalView` 里响应设置的 effect 只写了 `term.options.fontSize = settings.font_size`。字号一改字符格子就变大，**但容器像素尺寸没变**，所以唯一会去 `fit()` 的 `ResizeObserver` 根本不会触发 —— `cols/rows` 从此停在旧值。用户看到的是：把字号从 14 调到 22，右边一截内容再也不出现（被 `overflow:hidden` 裁掉），而远端 PTY 还按 110×23 在排版，`vim`/`htop` 画错、换行位置也不对。改字体（同一字号不同字宽）同理。

处理（只挪"谁来量"，不碰转发/渲染/输入）：

- `fit` 与"几何变了才回传 PTY"合并成一个 `refit()`：`fitAddon.fit()` → 比对 `cols/rows` 与上一次真正通知过的值 → 只有真变了才 `ssh_pty_resize`。`fit()` 抛错（隐藏面板量不出尺寸）时直接 return，**不会把 `cols=0` 发给远端**。
- 两条触发口共用这一个 `refit`：`new ResizeObserver(refit)`（面板拖动、隐藏面板重新显示）与新的 `useEffect(..., [settings.font_size, settings.font_family])`（设置里改字号/字体）。后者刻意排在写 `term.options.fontSize` 那条 effect 之后 —— effect 按声明顺序跑，早一步就量到旧格子。
- 卸载清理里把 `refitRef.current` 换成空函数，旧 `sessionId` 不会再被 resize（面板已经销毁、会话号还可能已被复用）。
- 顺带把"每次 ResizeObserver tick 都发一次 `ssh_pty_resize`"改成按几何去重：同一尺寸对 PTY 是幂等的，去重后"到底有没有重新量过"在审计/日志里看得见。

`tests/terminal-refit.test.ts` 22 例（`npm test` → **16 文件 / 503 例**），守的是"不会再退回两份事实"：`.fit()` 全文件只能有 2 处（连接时初测量 + `refit` 内）、`ssh_pty_resize` 只能有 1 处且必须在 `refit` 体内、`refit` 的 catch 里要先 return、ResizeObserver 用的就是 `refit`（不许另写一份）、按字号依赖的那条 effect 只能调 `refitRef.current()`（直接碰 `termRef`/`fitRef` 就是把回传拆出去）、且它排在写 `fontSize` 之后。这类顺序断言是本轮唯一的"隐性不变量"，没有守卫的话下次整理 effect 就会静默退回旧行为。

运行时证据（一次性 `.verify` 探针：给终端一个 900×420 的确定盒子渲染真实 `TerminalView`，stub `__TAURI_INTERNALS__` 记录每次 `ssh_pty_resize`，验完即删）：

- 修复后（900×420，DOM 渲染器，`.xterm-screen` 宽 / 容器宽 = 有没有被裁）：14 号字 `110×23`、屏宽 880 ≤ 900；调到 22 → 发出 `68×15`、屏宽 884；调到 11 → 发出 `136×30`。**每一步都恰好一条 resize，且屏宽始终不超容器**。
- 隐藏面板安全：`display:none` 时把字号改成 26 → resize 计数**不变**（3→3），此时 `.xterm-screen` 宽 0，证明确实没把垃圾几何推给远端。
- 对照组（只删掉那条按字号的 effect、`refit` 与 ResizeObserver 原样留着，重建 bundle）：改字号后 `ssh_pty_resize` 计数 **0**，屏宽从 840 涨到 **1365**（容器 900，溢出 465 px 被裁掉）。归因落在那条 effect 上，随后 `diff` 确认文件逐字节还原。
- 仍是 **Tauri 运行时未验证**，且这轮多一条明确的通道边界：**后台/隐藏标签页里 `ResizeObserver` 的回调不会被投递**（探针里把容器从 900 改成 700 再改回来，一个回调都没来）。所以"隐藏面板改字号 → 重新显示时补上几何"这条路径在本通道只有代码证据，没拿到运行证据；真壳 `npm run tauri dev` 里把它转成实测。

## 7.17 阶段五第十轮：字号缩放键 + 上下限收进单一真源（"能改字号"≠"能在打字现场改"）

上一轮把"改了字号之后几何会不会跟着变"修好了，但这轮先看的是操作面：**改字号只有一条路径 —— 打开设置弹窗、找到输入框、敲数字**。终端里正看着一行密密麻麻的输出想放大，代价是离开当前上下文开一个模态框；而 iTerm2/Terminal/VS Code 的用户预期都是 `⌘=`/`⌘-`/`⌘0`。同时 `8`/`32`/`14` 这三个数字散在设置页 `InputNumber` 的 `min`/`max` 和 store 的默认值里，各写一份：键缩到 33、输入框显示 32，用户就会认为"缩放把设置改坏了"。

处理（新增一个纯函数 + 三条绑定，不碰输入/网关/会话）：

- `src/utils/fontZoom.ts`：`FONT_SIZE_MIN/MAX/DEFAULT/STEP` 与 `stepFontSize(current, delta)`。设置页的 `min/max/step`、store 的默认值、键盘缩放三处全部改为引用它 —— 数字只有一份，越界一律贴边而不是拒绝。
- `stepFontSize` 对脏配置先 `Math.round`，读不懂的值（NaN/字符串，来自旧版落盘的 `settings`）回到默认再挪，避免 `14 + 1` 那类算式把 `NaN` 写回设置并持久化。
- `shortcuts.ts` 加 `zoom-in`/`zoom-out`/`zoom-reset`（group `layout`），并给 `Combo` 加 **`alt`**：它表达的是"同一个动作的第二个物理键"（`⌘=` 与 `⌘+`，后者是 `⌘⇧=` 交出来的字符和数字键盘的 +），**不是**另一条绑定的别名 —— 否则"组合键唯一"这条守卫就失去意义了。`matchesCombo` 里为它开一个窄口子：只在 combo 自身不许 Shift、且这次带 Shift 且 key 正好是 alt 时放行；`digit` 分支顺手补上 `!e.shiftKey`。
- `App.tsx` 的分支按 stale-closure 规矩全部走 `useServerStore.getState()`；`next !== cur` 才写设置（贴边时省一次 `persistSettings` 落盘，也免得设置页闪一下）。
- 设置页字号项加 `extra`：用 `comboLabel("zoom-in"/"zoom-out"/"zoom-reset")` 现场拼出键位提示，Mac 显示 ⌘、其它平台显示 Ctrl，与面板同源。

`tests/font-zoom.test.ts` 25 例：`stepFontSize` 的步进/上下限取整/NaN 与字符串回落到 `DEFAULT+1`，边界包含默认值，再加静态守卫 —— 源码里不许再出现 `min={8}`/`max={32}`/`font_size: 14` 字面量，缩放分支必须用 `getState()`、要 `preventDefault`、要走 `stepFontSize` 与 `FONT_SIZE_DEFAULT`、要有 `if (next !== cur)`、要 `return`。`tests/shortcuts.test.ts` 93 → **123 例**。

这一轮的测试改动里有一处是"守卫换真"：原来那条"表里不许有裸数字或符号"的断言被 `⌘0` 合法地撞到了。`⌘0` 不是例外，**问题在于那条断言查的是错的属性** —— 历史上的事故是"没有修饰键的 `Shift+3` 抢走了 `#`"，所以该查的是"裸按键必须命中 0 条绑定"。改成对 `["0","1","9","#","3","t","f","=","-","!","@","ArrowUp","ArrowRight"]` 逐个不带修饰键地过一遍，既留下 `⌘0`，也把"裸 `=`"这种新坑纳进来。另加 alt 撞车/alt 命中自己、10 条 zoom 匹配矩阵、3 条 `comboLabel`（`⌘=`、`Ctrl+-`、`⌘0`）。

运行时证据（一次性 `.verify` 探针：stub `__TAURI_INTERNALS__` 渲染**整个** `App.tsx`，记录 `save_settings` 调用与 `font_size`，验完即删）：

- 主路径：从 14 起 `⌘=` → 15、`⌘⇧=`（key `+`）→ 16、`⌘-` → 15、`⌘0` → 14；四次按键**每次都 `defaultPrevented: true`**，`save_settings` 计数 **4**（落盘确实发生）。
- 不许吃掉打字：不带修饰键敲 `=`/`-`/`0`/`+`，`defaultPrevented` 全为 **false**、`font_size` 不变 —— 终端里的 `make -j4`、`a=1` 不会被劫持。
- 不误伤邻居：`⌘1` 仍走切标签分支。
- 对照组（只删掉 `App.tsx` 里那条 zoom 分支、绑定表与 `fontZoom` 原样留着，重建 bundle）：`⌘=`/`⌘-`/`⌘0` 的 `defaultPrevented` **全为 false**，`font_size` 停在 14，`save_settings` 计数 **0**。即"表里声明了"≠"接上了线"，正是 `wiredIn` 守卫要防的那类漂移。随后 `diff` 确认分支逐字节还原，且还原后 `npm test` 仍 **17 文件 / 558 例全绿**。
- 通道边界（沿用 §7.16，本轮不重复索取）：整个 `App` 在无头后台标签页里视口量到 0×0，所以探针里的 `fit()` 只能给出 `2×1` 这类退化几何 —— 本轮证据只用于**字号与按键处置**，几何那一半由 §7.16 的定尺寸探针承担。
- 仍是 **Tauri 运行时未验证**：真壳里 `⌘=`/`⌘-`/`⌘0` 会不会被 WKWebView 自己吞掉没实测过（静态侧先排除了一个常见嫌疑：本应用没有设置原生菜单，`src-tauri` 里搜不到任何 accelerator/`MenuItem` 代码，`tauri.conf.json` 也没有 zoom 配置，所以不存在"原生加速键抢先"这条冲突路径）。缩放后 PTY 是否真的按新 `cols×rows` 重排（依赖 §7.16 那条 `refit`），也只有真壳能给出端到端结论。

## 7.18 阶段五第十一轮：外部配置进界面前必须先过闸（"配置里写了"≠"配置能用"）

缺陷形状：`settings` 是整棵应用里唯一一份"从磁盘来的对象"，但两个入口都没验过它 —— `loadConfig` 写 `{ ...defaultSettings, ...(config.settings || {}) }`（有兜底，但兜不住越界与类型错的值），`importConfig` 更直接 `settings: config.settings || defaultSettings`（整份替换）。于是三类**真实会出现**的输入能一路走到 xterm 和设置页：

1. 老版本/半成品导入件只写过当年那几个字段 ⇒ 新增项在 store 里是 `undefined`；
2. 手改过、或脚本批量改过的 `config.json` 把数字带出界（`font_size: 400`、`scrollback: -5`、`opacity: 9`）；
3. 布尔位被写成 `0` / `"off"` / `null`。

**为什么这轮值得做**：§7.16 刚把"字号变了要重量几何"接上，那意味着一份脏 `font_size` 现在会**把错的 `cols×rows` 回传给远端 PTY** —— 读侧的洞和写侧的修复一撞，破坏面从"显示不好看"变成"vim/htop 按 3×1 排版"。

运行时证据（一次性 `.verify` 探针：900×420 定尺寸盒 + 真实 `Terminal`/`FitAddon`，DOM 渲染器，量完即删）。左列是直接喂给 xterm 的选项，右列是量到的实际产物：

| 喂进 xterm | fontSize | scrollback | cols×rows | `.xterm-screen` 宽 |
| --- | --- | --- | --- | --- |

| B 缺字段（旧 partial 导入的形状） | **15** | **1000** | 98×23 | 885 |
| C `font_size: 400` | 400 | 10000 | **3×1** | 722 |
| D `font_size: 0` + `scrollback: 0` | 0 | 0 | 80×24 | **0（整块空白）** |
| E `font_size: "abc"` + `scrollback: -5` | "abc" | 1000 | 93×35 | 878 |
| F 过闸：14 / 10000 | 14 | 10000 | 105×26 | 885 |

- E 行的 `scrollback: -5` 也被 xterm 悄悄救回 1000，同一条"兜底在下游、上游看不见"的道理。

**一处必须澄清的自我修正**：我最初把这轮记成"脏配置会静默关掉安全网关"，**核对后不成立**。`commandGate.guardEnabled()` 早就写成 `settings.dangerous_command_guard !== false`（`command_history` 同），设置页各 `Switch` 也是 `!== false`，所以 `"off"`/`0`/`null` 都不会关掉网关 —— 对照组里 `decideCommand("rm -rf ./build")` 依然返回 `guard_level: "confirm"`、`approved: false`、无 `command_gate_bypassed`。真实受损的是**值本身**被污染（`strict_host_key: 0`、`log_redaction: null`、`dangerous_command_guard: "off"` 进了 store 和设置页，用户下次点保存就把这些垃圾值落回磁盘），以及数字/枚举原样流进 xterm。网关那层我没当成本轮战果。

处理（只加读侧闸，不碰下发口/网关/会话）：

- `src/utils/settingsSanity.ts`：`normalizeSettings(raw, defaults)` 一个函数 + 每张表（`NUMBER_RULES`/`BOOL_FIELDS`/`ENUM_FIELDS`/`STRING_FIELDS`/`NULLABLE_STRING_FIELDS`）和对应的上下限常量。`font_size` 直接复用 §7.17 的 `FONT_SIZE_MIN/MAX`，设置页五处 `min`/`max` 字面量（`SCROLLBACK`/`OPACITY`/`KEEPALIVE`/`CONNECTION_TIMEOUT`/`PTY_BATCH`）改为引用这里的常量 ⇒ **闸夹的范围和输入框能填出来的范围是同一个数字，改一处两处一起动**。
- 分类规则：布尔只认 `typeof === "boolean"`（**显式 `false` 是用户的选择**，§5.7 要求可回退开关；`0`/`"off"`/`null` 不是）；数值要求 finite 再夹取整（`keepalive_interval` 的 `null` 是"不发心跳"的合法表达，按 `nullable` 保留）；枚举走白名单；字符串要非空；**raw 里出现但表里没声明的键永不写入**（防的是"导入件多出一个键 ⇒ 变成 `settings.someNewThing`"这类反向污染）。
- 落点只有两个：`loadConfig`、`importConfig`（导入件可能整份 `null`，故 `config.settings` 一并改成 `config?.settings`，缺字段回落默认而不是 `undefined`）。`defaultSettings` 改为 `export`，给测试当字段清单真值用。

`tests/settings-sanity.test.ts` 96 例 ⇒ `npm test` **18 文件 / 654 例**（`npx tsc --noEmit` 0 错误，build 1,892.23 kB / gzip 570.31，比上轮 +1.51 kB）。三类守卫里两类是"防漏"而不是"防错"：

- **覆盖守卫从活的 `defaultSettings` 反推**：每个设置项必须落进某一张表（数值/布尔/枚举/字符串/可空之一）且互斥，默认值自身必须落在区间内 ⇒ 以后加设置项若忘了进闸，测试当场红，而不是等用户配出个脏值。
- **跨文件同步**：`THEME_IDS`/`CURSOR_STYLES` 与 `TerminalView` 的 `THEMES` 键、设置页下拉 option 逐项对齐。这里踩到一个新的假绿陷阱：`matchAll` 少写 `/g` 会返回**三万条空匹配且不抛异常**，测试一度报 `got: []`；已补一条"扫描确实抓到了东西"（`options.length > 10`）的断言 —— 正则退化从此不可能变成绿灯。
- 真 store 行为：打桩 `get_config` 返回中毒配置、`import_config` 返回只剩主题的旧导入件，断言夹取后的值、三个安全位仍为 `true`、没有任何设置项是 `undefined`，并跑一次 `decideCommand` 把"网关不受影响"这条钉住。

对照组（把 gate 换回旧的 merge 形状，另存 `serverStore.ts.ctl`，只跑该文件）→ **13 例红**，报错正是修复前的实测值：`脏配置里 strict_host_key: 0 没把 P0-1 关掉 got : 0 want: true`、`log_redaction: null got : null`、`dangerous_command_guard: "off" got : "off"`、`透明度也被夹住 got : 9 want: 1`、`导入只带主题时字号回到默认而不是 undefined got : undefined want: 14`、`回滚行数 got : undefined want: 10000`；而 `decideCommand` 那几例在对照组里**依然绿**，这就是上面那条自我修正的依据。随后还原并 `grep -c MUTATION-CONTROL` = **0**、`git diff --numstat` = 12/7，重跑全绿。

本轮没做与新的已知缺口：

- 只做**读侧**。写侧照旧：`custom_css` / `background_image` 从导入件进渲染器时，闸只保证它是非空字符串，没有 CSS 白名单或来源校验（要做就是独立一轮，且牵动 CSP）。
- 发现一个独立缺陷并**没有顺手改**：`importConfig` 只 `set()` 不 `persist`，导入重启即丢 ⇒ 记进 §7.6 已知缺口。
- 仍是 **Tauri 运行时未验证**：真壳里"导入他机 `config.json` → 设置页显示的是默认值而不是空/脏值"没跑过。本轮证据是**两端各测一次再组合**（node 层 store：脏输入 → 夹取后的值；浏览器层 xterm：夹取后的值 → 几何），没有把整棵 `TerminalView` 挂上真 store 跑同一条链 —— 因为两端的接缝正是 `settings` 对象的这几个键，而它们已被分别量到。

## 7.19 阶段五第十二轮：快捷命令下发口（"提示已执行"≠"命令发出去了"）

缺陷形状（这轮不是"值不对"，是**反馈在说谎**）：`executeSnippet(serverId, command)` 内部按 `tabs.find((t) => t.serverId === serverId)` 找标签，而它的**两个调用口交的都是 tab id** —— `App.tsx` 把 `activeTabId` 当作 `serverId` prop 传给 `SnippetsPanel`，命令面板写的是 `activeTabId || tabs[0]?.serverId`（两种 id 混在一个表达式里）。于是查找永远落空 → `if (!sessionId) return;` 静默返回，可 `handleRun` 在**发起之前**就已经 `message.success("已执行: xxx")`。

用户今天的体验：点快捷命令 → 看到绿色"已执行" → 终端里一个字都没有。§7.14 已经为这类形状抽过 `pickActiveSession()` 并写了守卫，但那份守卫只盯住了当时迁移的两个模态框，**下发口这一份复制品一直留在原地**。

更糟的一层（对照组才看出来）：旧写法在 `sessionId` 为空时就 return 了，**根本没走到网关**，所以危险命令的 Snippet 连"被拒绝"这件事都没进审计 —— 既没有执行也没有痕迹。

处理（收口成一个结论，不碰网关本身）：

- `executeSnippet(command)`：**去掉 serverId 参数**，目标会话只能来自 `pickActiveSession(get())`（活跃标签的活跃面板，回落主面板），主机清单改用 `sessionTargets([sessionId])`（同一份真源的另一视角，不再有"传入的 id 是什么"这种歧义）。TS 的元数检查从此替守卫站岗：任何调用方再传 id 就编译不过。
- 返回 `SnippetRun = {ok:true, sessionId} | {ok:false, reason:"no-session"|"cancelled"|"failed", error?}`；`ssh_pty_write` 改为 `await`，写失败（会话刚好断）从此冒泡成 `failed` 而不是只 `console.error`。
- 措辞收进 `src/utils/snippetRun.ts: describeSnippetRun()`，两个入口共用（否则又会分叉出两份"要不要报成功"的判断）。
- **文案改成"已发送到当前会话"**：前端只把命令写进了 PTY，远端跑没跑成、退出码是什么一概不知道 —— 原来说"已执行"是越权承诺。三种未发出的原因分别给 warning / info / error，都不许是 success 语气。

## 7.20 阶段五第十三轮：确认请求排队（「弹了确认框」≠「每条命令都被问过」）

形状：`DangerConfirm.tsx` 文件头写着「用一个模块级队列把命令式的 `confirmDangerousCommand()` 挂到 React 树上」，实现却是 `const [req, setReq] = useState<Request | null>(null)` + `enqueue = (next) => setReq(next)` —— 单槽直接覆盖。**注释承诺的是队列，代码给的是槽位**（§7.19 已把它列进待办）。

为什么这是缺陷而不是「少个排队功能」。并发确认在真实路径上可达，且不止一条：

- `confirm` 级弹窗里没有 `autoFocus` 输入框，焦点仍留在 xterm 自己的 textarea 上 → 第一条挂着时用户照常能在另一个面板（⌘⇧←/→ 换活跃面板是 window 级快捷键，Modal 拦不住）敲出第二条危险命令；
- `TerminalView` 的粘贴兜底写的是 `void approveCommand(...)`（不排队、不等上一条）；
- 命令面板 / Snippet / 批量与手输混用同样会叠。

被顶掉的那条不是「晚点问」，而是三件事同时发生：① 它的 promise 永不 settle → 那条命令既没执行、`decideCommand` 也就没走到 `auditEvent`，**审计里一个字都没留**（P-2 + T-4-7 双缺口）；② 调用方的 `await` 永久挂起；③ `LineInputGuard` 的 `buf` 停在被扣下的那一行不清，此后该面板每次回车都被同一个已死的 await 扣住 —— 表现为「终端突然打不动字」，而屏幕上那句命令还在。

处理（把排队语义从组件里挪出来，好测、也好钉）：

- 新增 `src/utils/confirmQueue.ts: ConfirmQueue<T>`（纯逻辑：`head / depth / queued / push / settleHead / close / subscribe`）。契约是**每条请求最终都必须 settle**；`settleHead` 先出列再回调，所以回调里再 push、甚至再 settle 都不会丢条目或重复结算（有对应用例）。
- `DangerConfirmHost` 改用 `useSyncExternalStore` + 模块级稳定 `subscribe/headSnapshot/depthSnapshot`，队首即 `open={!!req}` 的唯一依据；组件里不再有可被覆盖的请求 state。
- 宿主卸载的 cleanup 里 `queue.close()`：留在队列里的全部 fail-closed 结算。调用方拿到 false 后走的是它自己那条「已取消」分支，所以审计照样记 `approved:false` —— 不再需要「顶掉时补一条审计」这种补丁，因为「被顶掉」这个状态被消掉了。
- 结算同一处补 `setTyped("")`：block 级的逐字确认输入必须跟着队首归零，否则下一条 `mkfs` 会看到上一条敲过的「确认执行」。顺序被测试钉住（先 `settleHead` 再清零）。
- 标题加「还有 N 条待确认」（`Math.max(0, depth - 1)`）：让「关掉这条后面还有」可见，否则用户会以为确认框总共只有一个，第二次的点击对象其实换了命令。

## 7.21 阶段五第十四轮：关闭确认闸（「点了 ×」≠「用户知道自己要断几条会话」）

形状：`×`、⌘W、右键「关闭标签页 / 关闭其他 / 关闭右侧」、分屏面板的关格、删除服务器引起的连带关闭 —— 五条路径都是**直接 `ssh_disconnect`**。跑在半路的 `mvn package`、没 `COMMIT` 的事务、挂着的 `tail -f`，在一次点击之后没有拦路问题。危险命令有网关（§7.4、§7.20），断会话反而没有，边界是反的：误发一条命令还能 Ctrl-C，误断一条会话只能重连并从头再来。

三条设计约束（写进 `closeGuard.tsx` 文件头，也各自有用例）：

- **同源**：闸只有一道，放在 store 的 `closeTab/closePane` 里，而不是五个调用点各写一遍 `Modal.confirm`。调用点越多，越容易有一条忘记（`disconnectServer` 一开始就想弹框 —— 它已经弹过一次「删除服务器」了）。
- **无会话不问**：没有活着的会话就没有可丢的东西，弹框只会训练用户闭眼点「确定」。`tab.panes` 里没有 `sessionId` → `needsConfirm:false`，直接关。
- **一次意图只问一次**：批量与级联不得二次弹框。`closeTabs` 一次问完整批；`closePane` 关到最后一格时把会话交给 `closeTab` 处理并带 `force:true`，不再自己断一遍。

## 7.22 阶段五第十五轮：重连过程可见化（「后台在重试」≠「用户看得见在重试」）

### 缺陷形状

`reconnectPane` 顶部自己 `await sleep(backoffDelay(attempt))`，而排队的 `planRetry` 已经按**同一份**退避表等过一遍了 —— 同一个等待被算了两遍。实测（假时钟数相邻两次 `ssh_connect` 的间隔）：

| | 第 2~6 次尝试的实际间隔 |
| --- | --- |
| 声明的退避表 | 2000 / 4000 / 8000 / 16000 / 30000（封顶） |
| 修复前 | **4000 / 8000 / 16000 / 32000 / 60000**（恰好 2×，封顶档已越过 30 s） |
| 修复后 | **2000 / 4000 / 8000 / 16000 / 30000**（与声明一致） |

另一半是：这期间屏幕上只有一个红色「操作失败」面板。自动重连在后台跑，而"还有下一次"和"已经放弃、得我自己点"两种状态的外观**完全相同** —— 用户唯一的线索是一块会自己消失的错误面板。

### 立下的四条规矩

1. **等待只由一处调度**：`planRetry` 的定时器是唯一的等待来源，`reconnectPane` 里不再 `sleep`（静态守卫钉住 `backoffDelay(` 在 store 里出现 0 次、`nextReconnectPlan(` 恰好 1 次）。
2. **后台在跑就要说出来**：`reconnectProgress`（运行中 / 倒计时 / 已停止）由 store 写，面板与顶部状态条都只从 `describeReconnect()` 取话，两边不许自己拼「第 N 次」。
3. **停止原因三种不许共用一句**：`off`（没开自动重连）/ `limit`（到上限）/ `failed`（用户手点这一发失败）各自一条文案。这条是浏览器实测抓出来的 —— 第一版把 `auto` 记成"这次是不是自动触发的"，于是在**根本没开自动重连**的机器上屏幕写着「已连续 1 次连不上，自动重连已停止」，凭空捏了一条从没存在过的链路。改成由调度侧（唯一知道 `settings.auto_reconnect` 的地方）写 `reason`。
4. **「立即重试」只有在真排上下一次时才成立**：`retryLabel={isCountingDown(reconnect) ? "立即重试" : "重试"}`。旧写法判的是"有没有进度记录"，于是停止态也会说"立即重试"——可并没有一个"稍后"在等着被提前。

进度是运行时投影：故意不进 `tabs`，因此不会被 `persistTabs` 写进配置（重启后一个过期 `nextAt` 会显示成「还有 -37 秒重试」）。这条由断言实际 `save_tabs` 载荷的用例钉住，而不是靠正则扫源码。

## 7.23 阶段五第十六轮：终端搜索的"高亮"原来不存在（「扫到了」≠「看得见」）

### 缺陷形状

`TerminalSearch` 的注释自述"通过 highlight 整行的方式做伪高亮"，实际一行都没 highlight —— 组件算出 `matches` 之后只调 `term.scrollToLine(line)`，除了滚一下屏幕，没有任何视觉痕迹。用户按下 Enter 得到的"下一条"是一句文案数字在跳，屏幕上找不到对应的那块字。顺带查出四条同源缺陷：

1. **没有选中**：`Match.index`（累计字符偏移）算完就丢，`startCol`/`length` 从没交给 xterm。而选中才是 xterm 唯一的高亮 API（`select(col, row, len)`，`row` 是 **0-based 绝对 buffer 行**，不是"从底部数"）。
2. **方向反了**：匹配按 `line` 升序（0 = 最底/最新）存，"下一条"却按数组索引 +1 走 ⇒ 每按一次"下一条"往屏幕**上方**跳，而按钮图标是 `ArrowDownOutlined`。
3. **滚过去仍然被搜索框盖住**：`scrollToLine(line)` 把目标行顶到视口第一行，而浮层就压在右上角。留白原先写死 2 行，实测默认字号下浮层下沿压在 70 px = 3.9 行处（cellH 18 px）⇒ **写死的几何常数扛不住字号变化**。
4. **关掉之后焦点蒸发**：`onClose` 只把 `open` 置 false，焦点留在已经卸载的输入框上（浏览器把它交给 `body`），此后再敲键盘既不进搜索也不进终端；而且关闭时不清选中，屏幕上永远留着一块"来历不明的高亮"。

外加一条只在改的过程中才暴露的：**每渲染重搜一遍**。`runSearch` 依赖 `getLine`/`getLineCount`/`scrollToLine` 三个**每次渲染都换身份**的箭头函数，于是任何一次父组件重渲染都会重新全 buffer 扫描并把指针 `setCurrent(0)` 弹回最上面一条 —— 用户视角是"我什么都没按，位置自己跳了"。

### 立下的三条规矩

- **报的数必须等于真能跳到的数**：命中数触及 `SEARCH_LIMIT` 时 `findMatches` 返回 `truncated: true`，文案变成 `N / N · 已到扫描上限，更早的匹配未计入`。扫描是从最新往最旧，所以被砍掉的那一头**必须在文案里指明是"更早"**，不能只说"还有更多"。
- **坐标约定只许在一个地方写死**：`line = 0 = 最底下一行`（沿用旧 buffer 访问口）只出现在 `src/utils/terminalSearch.ts`，`findMatches` 内部把行序倒过来 ⇒ 返回的 `matches` 已经是"屏幕从上到下"，组件与 `TerminalView` 都不再做第二次翻转。
- **凡影响"看得见"的量，按实测几何算**：`coveredRowsOf({overlayTop, overlayHeight, containerHeight, viewportRows})` 用浮层下沿 ÷ 实测行高算留白行数（量不到几何 —— 容器 0 高 —— 才退到 `SEARCH_REVEAL_HEADROOM_FALLBACK = 4`），`revealScrollTarget` 再加一条"**已经在没被盖住的区域里就别动**"（每按一次 Enter 整屏跳一下很难读），最后夹进 `[0, bufferLength - viewportRows]`。

### 分层与接口

- 判定层 `src/utils/terminalSearch.ts`（新增，纯函数、不碰 xterm/DOM）：`findMatches` / `initialIndex` / `stepIndex` / `revealScrollTarget` / `coveredRowsOf` / `describeSearch`，文案的四态也在这里。
- 组件层 `TerminalSearch.tsx`：props 从 `scrollToLine` 换成 `revealMatch` / `clearHighlight` / `returnFocus`；`wasOpenRef` 保证"从未打开过的常驻隐藏面板"不会在挂载时抢焦点（`TerminalView` 每面板一个实例、非活跃标签只 `display:none`）。
- 视口层 `TerminalView.tsx`：`bufferApi` 收进 `useMemo(…, [])`（身份稳定），`revealMatch` **先 `select` 再 `scrollToLine`** —— 反过来会把"看不见的高亮"留在原地。

## 7.24 阶段五第十七轮：命令面板给每条会话都发了一张「当前」（「列出了」≠「说对了」）

### 缺陷形状

`CommandPalette.tsx` 里那条标签的判断是 `item.type === "server" && item.id.startsWith("tab-")` —— 前缀一命中就渲染 `<Tag>当前</Tag>`，**从头到尾没跟 `activeTabId` 比过**。于是开着 4 个标签页时面板里有 4 条都写着"当前"。这不是"样式丑"，是一句**没有指涉的断言**：「当前」是一个只能有一个指涉的词，屏幕上出现 4 个它，等于 4 个都在说谎。同一处还有第二条：分组标题写「已连接会话」，底下照旧列出 `state: "connecting"` 和 `state: "error"` 的标签页（断线重连到上限后就是 error 态）——组名替条目做了它们自己没做的保证。

顺带查出第三条更隐蔽的：**说明句和标签各说各话**。`description` 对每一条都写死"切换到此会话"，被标了「当前」的那条也照样写着"切换到此会话" —— 面板一边说"这是当前"，一边让你"切换到此会话"。

### 立下的规矩

- **单指涉词必须单指涉**：凡是"当前 / 已连接 / 唯一"这类只能落在一处的说法，判定必须显式比过真源（这里是 store 的 `activeTabId`），并且有一条测试穷举"活跃项换成任何一个值时，命中数恒为 1"。
- **不从字符串前缀猜类型**：条目"指向哪个标签页"改由 `CommandItem.tabId` 字段承载。测试专门断言 `isCurrentTab({ id: "tab-t-1" }, "t-1") === false` —— 长得像 `tab-` 不算，字段才算；否则下一次改 id 方案就会静默复发。

## 7.25 阶段五第十八轮：按 ↓ 高亮却往上跳（「排好序」≠「眼睛和手在同一份列表上」）

### 缺陷形状

上一轮把"说了什么"修对了，这一轮量的是"点得到吗"。组件里有**两条顺序**：`filtered` 是 score 序（键盘、Enter、行首序号都读它），`grouped` 是一个键序写死的对象字面量 `{已打开会话, 服务器, 代码片段, 操作}`（屏幕按它分块渲染）。两条顺序各自成立，却互相不知道对方存在。

真实 DOM 里量到的现场（输入 `db`，命中 3 条：会话 prod-db、服务器 backup-store、片段 db-recover；score 最高的其实是片段）：

| 状态 | 高亮落在哪一行 |
| --- | --- |
| 刚输完 `db` | 键盘第 0 位 = 视觉**第 3 行**（`2:db-recover`），前两行明明更靠上却"不是候选" |
| 按第一次 ↓ | 高亮**往上**跳到视觉第 1 行（`0:prod-db当前`） |
| 按第二次 ↓ | 视觉第 2 行（`1:backup-store`） |

也就是说 ↓ 的方向和屏幕上的方向相反；而在视觉第 3 行上按 ↑ 会原地不动（键盘已经到底了），用户只会觉得"这键坏了"。这不是排序不好，是**一个列表有两个真源**，必然分家——写死的类别优先级还把 score 的相关性整个推翻：越相关的片段越被排到下面。

### 立下的三条规矩

- **一个面板只许有一条序列**：先分块、再把分块结果展平成 `ordered`，渲染、键盘走位、鼠标 hover、行首序号全部读它。分块只是往序列里插标题，**不再另起一套顺序**。
- **组序由"首次出现"决定，不写死类别优先级**：相关性已经由 score 表达过了，再按类别压一遍等于把搜索结果重排。所以 `groupInOrder` 内部一次都不排序（测试直接守卫这一点）。
- **高亮必须看得见**：↑/↓ 走到哪一行，那一行就得被滚进窗口（`scrollIntoView({ block: "nearest" })`）。顺序对齐了但停在视口外，等于仍然没走到——所以这一条和上一条是同一个缺陷的两半，本轮一起修，并单独做了对照组。

### 分层与接口

## 7.26 阶段五第十九轮：搜索结果随新输出过期（「扫到了」≠「那一行还在原地」）

### 缺陷形状

§7.23 留下的那条遗留，这轮还。行坐标沿用 buffer 访问口的老约定：`line = 0` 是最底下（最新）那一行 —— 于是**这个坐标系只在扫描那一刻有效**。远端又推几行，底边往下走，同一个 `line` 指向的就是别的行；把旧行挤回滚出去则不改变底边相对行号。这轮先用探针把这条证伪做实（真 xterm + 真 `TerminalView` + 真 `ptyBus` 写入通道，vite 自建端口 8945）：

| 现场（修复前） | 面板说的 | 屏幕上真被选中的 |
| --- | --- | --- |
| 40 行、`ERR_` 命中 3 条，追加 15 行后连按三次「下一条」 | `1 / 3`、`2 / 3`、`3 / 3` | `er-1`、`er-2`、`er-3`（从 `filler-N ok` 上截出来的碎片，一个都不是当初的命中） |
| 单条命中 `ERR_alpha`，追加 8 行后按两次 | 两次都写 `1 / 1` | 两次都是 `er-12 ok` |

数字没撒谎（扫描当时确实 3 条），撒谎的是**指针**：那一行早就不在那儿了。形状上仍属"反馈与结论不一致"，只是这次骗人的不是排序、是坐标系。

### 立下的三条规矩

- **每条命中自带锚点**：`SearchMatch.text` 存扫描那一刻的整行原文。行号易腐，文本不易腐。
- **每一次跳转前一律先对回现实**（不是每次扫描）：`reanchorMatch` 以整行**逐字相等**为准，从原坐标由近及远找"还是那一行"的位置，并在新行上重算列号；认得回来就跳对的位置，并把修正后的坐标**写回结果列表** —— 否则下一次跳的还是旧坐标。
- **认不回来只许说认不回来**：绝不照旧坐标跳，也绝不拿近邻冒充。此时重扫一次，指针落在离原来最近的那条（`nearestIndex`），状态行如实标注「原结果已滚出缓冲区，清单是重新扫描的」；重扫后一条不剩就是「无匹配」，不许留着旧的 `3 / 3`。

### 分层与接口

- 判定层 `src/utils/terminalSearch.ts`：新增 `reanchorMatch`（+ 私有 `nearestCol`：同一行多命中时取离原列号最近的那个）、`nearestIndex`、`Reanchored { match, moved }`；`findMatches` 每条命中带 `text`，**同一行的多个命中共用一个字符串引用**，不是每条复制一份整行。`describeSearch` 多一个可选 `lost`，`truncated` 与它并列成 `notes[]`，用「 · 」拼，旧文案逐字不动（`terminal-search` 那 96 例里钉着）。

### 遗留（如实标注）

- 面板上的**条数**仍是"扫描那一刻"的条数：新输出把命中挤掉后，下一次跳转之前那个数字是旧的（跳转本身会自愈并重扫）。要在每次输出上刷新就得订阅 `onLineFeed` 全扫，刷屏日志下会把主线程吃满 —— 本轮明确不做。

## 7.27 阶段五第二十轮：SFTP 传输进度原来是装的（「画了进度条」≠「进度和成败是真的」）

### 缺陷形状

`git diff` 里那五行被删掉的旧代码就是本轮的靶子（上传、下载、批量下载、编辑拉取、编辑回传各一份，形状完全相同）：

```ts
setTransfer({ type: "upload", filename, progress: 0 });
await invoke("sftp_upload", { sessionId, localPath, remotePath });
setTransfer((prev) => (prev ? { ...prev, progress: 100 } : null));
message.success(`上传成功: ${filename}`);
// finally: setTimeout(() => setTransfer(null), 800)
```

- **进度是写死的两个数**：后端 `sftp_upload`/`sftp_download` 当时只是 32 KB 的复制循环，一条事件都不发。于是 45 MB 和 3 KB 的文件显示的是同一个 `0 → 100` 空跳 —— 进度条存在，进度不存在。
- **成功也是写死的**：两个命令返回的都是 `ExecResult`（**永不 reject**），前端却只有 `try/catch`。`catch` 是死代码 ⇒ 后端明确回 `success:false`（磁盘只读、会话已断、远端权限不足）时，屏幕上照样弹「上传成功」，进度条还停在 100。这是"反馈与结论不一致"里最贵的一种：用户以为传上去了。
- **上一条的定时器抹掉后一条**：`finally { setTimeout(() => setTransfer(null), 800) }` 无条件清空"当前那一条"。批量上传两个文件时，第一个的收尾定时器必然落在第二个的传输期间 —— 正在跑的进度条凭空消失。
- **拉取失败照样往下走**：`handleEditFile` 把远端文件下载到临时目录后不看结果就打开编辑器；三文件监听器发现本地改动后自动回传，失败也照旧推进 `lastModified` ⇒ 远端还是旧的，本地却再也不认为它需要上传。
- **`basename` 在 TS 里又抄了一遍**（`split("/").pop() || split("\\").pop() || "file"`），`formatSize` 也是面板私有的一份 —— 同一份逻辑多处复制正是上面那些分叉的温床。

### 立下的三条规矩

1. **进度只从后端来**：`pump_with_progress` 每 32 KB 块累计字节，按 `SFTP_PROGRESS_INTERVAL_MS = 250` 节流（首块必发、`transferred >= total` 必发，其余按 250 ms 间隔），前端只把事件灌进状态机，一个数字都不自己写。
2. **认不出的值一律不猜**：载荷缺 `session_id`、字节数不是 `number` ⇒ 丢弃；`total <= 0` ⇒ `percentOf` 返回 `null`，画一根没有填充的占位轨 + 文案「大小未知」，不给百分比；`ExecResult.success !== true` ⇒ 按失败处理，`error` 缺失时只说「传输失败」。
3. **一次操作一个身份**：`transfer_id` 由面板自己的单调计数器发出并随 IPC 带上，事件按 `session_id + transfer_id` **严格**认领（字符串 `"1"` 不算匹配）；结算与清除都要 `id` 对上才动手 ⇒ 上一条的 800 ms 收尾定时器不可能抹掉后一条，一条迟到的旧事件也不可能给新传输刷字节。

## 7.28 阶段五第二十一轮：一次"编辑远端文件"发出去三个路径，两个能逃出沙盒（「校验过了」≠「校验用上了」）

### 这一轮查的是什么

§7.27 收口时记下一条"待办"：`sftp_download` 的落盘路径没人管。动手前先把那条待办证伪了一遍 —— 结论是它比写下来时更糟，而且是**三件事叠在同一条链上**：

1. **写侧白名单形同虚设**：`paths::resolve_for_write` 有实现、有单测、注释写着"父目录后续按需创建"，`grep` 全仓 **0 个调用方**。`sftp_download` 把 `local_path` 原样交给 `tokio::fs::File::create`。
2. **目录没人建**：`handleEditFile` 算出的 `${tempDir}/z-terminal-edit/xxx` 深两层，干净安装上两层都不存在 ⇒ 双击编辑**必失败**（`No such file or directory`），而失败信息只出现在传输条上。
3. **远端文件名直接决定本地目录结构**：目录列表由 SSH 服务器给，`entry.name` 是最不可信的输入。旧拼法实测产出 `/var/folders/m9/T//z-terminal-edit/../../../../etc/passwd`（含 `..` 与空片段），穿越不在校验之前也不在写之前 —— 是**根本没有"之前"**。
4. **同名即同身份**：`/opt/app/nginx.conf` 与 `/etc/nginx.conf` 都落到 `z-terminal-edit/nginx.conf`。前一份还没关，后一份就把它顶掉；更糟的是 A 的监听器每 3 s 检查那个文件，一旦用户改了 B 的内容，**A 的 watcher 会把 B 的内容上传回 A 的远端路径**（两份副本互覆）。

### 修法

- `src-tauri/src/paths.rs`：新增 `prepare_write(path)` 作为**唯一落盘闸** —— 先 `resolve_for_write`（白名单 + 拒 `..` + canonicalize 收容），再把缺失父目录 `0700` 递归建出来，返回真正要写的 `PathBuf`。`write_private_key` 原先把这两步写在自己函数体里，现在改为调用同一道闸；`ensure_parent_dir` 从"单层 `create`"修成**递归**（编辑副本是两层缺失，单层必然 `NotFound`，而调用方只能看到一句没头没尾的"创建目录失败"），错误文案补上具体路径。会话层（`ssh.rs`）保持原样：它只 `File::create`，既不校验也不建目录 —— 闸放在命令层，任何调用方都覆盖得到。
- `src-tauri/src/commands.rs`：`sftp_download` 在**命令层**过闸（这样任何调用方都覆盖得到），写的是闸返回的 `target_str` 而不是入参 `local_path`；闸拒绝时回 `ExecResult{success:false, error}` 而非 `Err` —— 这条命令的返回类型决定它永不 reject，抛出去前端读不到原因（§7.27 的 `transferFailure` 正是靠 `.success` 上屏）。
- `src/utils/sftpEditPath.ts`（新）：把"远端名字 → 本地落点"定成三条规则 —— ① 远端名字不许决定目录结构（`basenameOf` + 控制字符/`/\:*?"<>|` 逐个替换、去尾部的点与空格、超长截断后拼哈希）；② 一次编辑一个身份（`会话 id + hash8(remotePath)` 作目录名）；③ 不产空片段（任何一步退化成空都用 `file`/`session` 兜底）。分隔符与控制字符一律改写，`;` `&` 保留 —— 这个串从来不进 shell，把它当 shell 参数担心是错的口径。

## 7.29 阶段五第二十二轮：SFTP 面板的会话身份处处是错的，修好它又带出一个无限重传（同一个参数在多个调用点上有两种语义）

### 这一轮查的是什么

§7.28 收尾时用浏览器探针量"编辑远端文件"的真实 IPC 报文，顺带发现一个更根本的事实：**`SftpPanel` 的 prop 名叫 `serverId`，但三个调用点喂进去的东西不是一回事**。

- `App.tsx` 工具栏按钮与 ⌘⇧E 传的是 `activeTabId`（标签页 id）；
- 标签页右键菜单传的是真 `serverId`；
- 面板内部、以及 `serverStore.listSftp` 内部，都按 `tabs.find((t) => t.serverId === 该值)` 找会话 —— 而 `tab.id` 由 `genId()` 生成，与 serverId 不是一套编号。

于是同一份查找在两条路上传入**恒不匹配**的值。真 `App` + 真 `SftpPanel`（只 stub IPC）实测：

| 场景 | 修前 | 修后 |
| --- | --- | --- |
| 点工具栏 SFTP | `{sftpVisible:true, sftp_list 次数:0, 行:0, 提示:无}` —— 面板开了、目录永远列不出来 | `sftp_list` **1 次** `{sessionId:"sess-1", path:"/"}`，2 行文件上屏 |
| 按 ⌘⇧E 开 | `sftp_list` 0 次（`ls(aId,"/").catch(()=>{})` 把「会话不存在」整个吞掉） | 开：`sftp_list` 1 次（sess-1）；关：0 次 |
| 面板里双击进目录 | 新增请求 0 次，只弹一条 `获取文件列表失败:Error:会话未连接` | `sftp_list` 1 次 `{sessionId:"sess-1", path:"/dir-1"}`，`sftpPathBySession` 记下这一级 |
| 切到另一个标签页 | —— | 只列自己那台：`{sessionId:"sess-2"}`，行从 `one.txt/dir-1` 换成 `two.txt`；切回 tab-a 直接回到 `/dir-1` |
| 拿 tab id 去列目录 | 悄悄"成功"（旧实现按 serverId 找不到就回落第一个同服务器标签页） | 如实抛 `会话不存在: tab-a`，且**不污染**当前列表（归属仍是 sess-1，行不变） |

关键在于：这不是"某个按钮不好使"，而是**整个面板在已连接的会话上做不了任何事**（下载、上传、新建、重命名、编辑一律报「会话未连接」），而终端本身是连着的。三处复制的查找 + 两种参数语义 = 缺陷温床，和 §7.24 的端口转发面板是同一类。

### 顺手挖出来的第二个缺陷

身份修好后，编辑监听器回传走的是**实时** `getSessionId()`（"面板当前"的会话）。修前它恒为 undefined 所以没人察觉；修后它会在人切走标签页之后，把 A 主机的编辑副本推到 B 主机的同名路径上 —— **修一个缺陷会解锁另一个**，所以两件事必须同轮落地。

取数过程中还撞到第三个：`watcher` 每 3 s 比较 `currentStat.modified > lastModified`，而 `lastModified` 是闭包里的 `const`，"成功后推进"只写进了 React 状态那份（监听器从不读回来）。实测：**本地保存一次，13 s 内发出 8 次 `sftp_upload` + 8 条「已自动上传更新」+ 8 次列表刷新**，只要面板开着就永远不停。这条与身份无关，是 §7.27/§7.28 那两轮都没看到的存量缺陷。

### 修法

1. **身份单一真源**：`src/utils/session.ts` 拆出 `pickTabSession(state, tabId)`（按指定标签页取其活跃面板会话，回落该页主面板会话），`pickActiveSession` 变成它的转发；取不到就是 `undefined`，**绝不回落到"随便哪个同服务器的标签页"**。面板 prop 改名 `tabId`，`getSessionId`/渲染期身份全部走这一个函数。
2. **列表有归属**：`listSftp(sessionId, path)` 参数语义改成 sessionId（不再自己猜标签页），成功时把 `sftpSessionId` 与 `sftpPathBySession[sessionId]` 一起写回。面板读列表时先过归属闸：`sftpSessionId !== activeSessionId` 就当"还没列过"（行为 `NO_ENTRIES`、路径为 `/`）—— 否则切标签页的一瞬间，旧会话的文件名会配上新会话的 sessionId。
3. **面板自己列目录**：`App` 那三处顺手 `listSftp(...).catch(() => {})` 全部删掉，改由面板的对齐 effect 发起（纯函数 `listingCandidates` 定顺序：先回该会话上次浏览的那一级，列不成再退回根）。失败原因不再只闪过一条 toast，而是留在空态上（`无法读取目录 /：Permission denied (os error 13)`）；没有会话时空态写「会话未连接」，不再谎报「目录为空」。
4. **一次操作一个身份**：编辑回传用**开编辑时捕获**的 `sessionId`；`EditingFile` 加 `sessionId`，去重、推进、关闭都按 `(会话, 远端路径)` 两条键（两台主机可以都有 `/etc/hosts`，只用 `remotePath` 当 key 会撞 key，且关闭其中一个会把另一条从列表抹掉而它的定时器还在跑）。跨会话存活的条目在标签上标出主机名（实测 `one.txt@alpha`）。会话断开则停止监听并说明"改动不会自动回传"。上传后的列表刷新改按 store 现值核对（闭包里的 `navigateTo`/`getSessionId` 属于开编辑那一次的 tabId，切过标签页再用会引发 `sess-2 → sess-1 → sess-2` 三次列目录 + 面板闪一下）。
5. **回传只做一次**：监听器自有可推进基准 `pushedModified`，并加在途标记 `pushing`（一次上传超过 3 s 时不得并发推同一条）。

## 7.30 阶段五第二十三轮：批量下载点 10 次对话框，而"选一次目录"会把本地文件悄悄换掉（§7.27 遗留的第 1 条）

### 这一轮查的是什么

§7.27 记下的遗留第 1 条：**批量下载对每个文件弹一次原生保存框**。多选 10 个文件就要点 10 次对话框，而且中途某次取消只表现为 `continue` —— 少下了几个，屏幕上没有任何解释。

改成"选一次目标目录"是显然的，但**那道兜底也就没了**：单文件路径上，"要覆盖吗"是 NSSavePanel 在问；批量路径上，落点文件名由**远端目录列表**决定，直接拼进用户挑的目录，等于让远端决定本地写哪、写掉谁 —— 这正是 §7.28 刚清掉的那一类（远端可控文件名参与本地路径）。所以两件事必须一起做：一次目录选择 + 不静默覆盖。

### 修法

1. **面板侧**：`handleBatchDownload` 只弹一次 `open({ directory: true })`；落点名字由新纯函数 `src/utils/sftpDownloadPlan.ts` 决定 —— `planDownloads` 复用 §7.28 的 `safePathComponent` 净化，并做**批内去重**（`a*.txt` 与 `a:.txt` 净化后都是 `a_.txt`，不去重就是后一个盖掉前一个），改过名的条目带 `renamed` 标记；`joinDownloadTarget` 处理目录选择器返回的尾分隔符形状（`/` 与 `\`，多个也只吃一个），拼出来不含 `//`。
2. **后端侧**：`sftp_download` 新增 `overwrite: Option<bool>`；`Some(false)` 时走新的 `paths::prepare_write_new`（同 `prepare_write`，但目标已存在即拒 `目标已存在: <路径>`）。判存在用 `symlink_metadata` 而不是 `exists()` —— 指向不存在文件的悬空符号链接 `exists()` 说不存在，跟着它写就是"穿过链接落到别处"。单文件那条显式传 `overwrite: true`（覆盖的决定已由原生保存框做过），编辑副本那条一字未动。
3. **反馈**：本地已有同名文件时**先探测再跳过**（只为把原因说清楚，兜底仍在后端，因为探测与写入之间文件可能刚被别的东西建出来），最后一句汇总 `已下载 N 个到 <目录>；跳过 M 个（本地已存在，未覆盖）：…；失败 K 个：…`，成功/警告/错误三态由 `summarizeBatch` 决定 —— 只要有一件没成就不是 success。

### 证据

## 7.31 阶段五第二十四轮：「导入成功」其实换掉了全部配置，而交回前端的凭证是密文（顺带炸出脱敏器在中文行上 panic）

### 这一轮查的是什么

先纠正 §7.6 的一条**过时结论**：它记着「`importConfig` 只落到内存，不持久化」。核对代码后是反的 —— Rust 侧 `import_config` 一直会 `save_config`（含备份 + 封存 + 原子写）。真正的缺陷是另外两个：

1. **交回前端的凭证是磁盘态密文**。`import_config` 把刚 `serde_json::from_str` 出来的结构原样 `Ok(config)` 返回，而磁盘态里 `password` / `private_key` / `api_key` 都是 `enc:v1:…`。前端 `set({servers})` 之后，界面拿密文当密码用 ⇒ **导入完所有服务器都连不上**（要重启才会走 `load_config()` 解密），且下一次 `save_servers` 会把这段密文再封一层（`seal_secrets` 认不出它是本机密文）。
2. **整份覆盖没有任何确认，也不留审计**。导入会一起换掉服务器、设置、片段、AI 配置与 tab 布局，旧写法选完文件直接写，一句「导入成功」才让人意识到列表被换了；而 `export_config` 两边都有审计（P-4 里"导出必须留痕"），导入反而没有。

给 import 补审计之后又炸出第三个 —— **`redact.rs` 在含非 ASCII 的行上直接 panic**：`mask_bearer_tokens` 把 `chars` 拼回一个 `String` 当 `lower`，再用**字符下标**去切（`lower[i..]`）。行里只要之前出现过中文，字符下标就不再落在字节边界上：

```
panicked at src/redact.rs:294: start byte index 1 is not a char boundary; it is inside '导' (bytes 0..3)
```

这不是探针环境特有的：审计与日志里的中文行是本项目的常态（`导入配置失败: 解析失败 …` 就是现成的触发样本），也就是说**任何一次"带中文的失败信息经过脱敏器"都可能让那次记录炸掉**。§7.16 那 10 例脱敏测试全部只用 ASCII 样本，所以两年没被发现。

### 修法

1. `import_config` 改成 `save_config(解析结果)` 之后 **回读 `load_config()` 再返回**（与启动时同一份视图），并按 `export_config` 的对称写法把成功/失败都写审计（成功带真实台数与片段数）。坏文件在 `save_config` **之前**就被挡掉，不会把现有配置冲成空。
2. 前端 `importConfig` 返回 `ImportSummary { servers, snippets, needsCredential }`。`needsCredential` 数的是"回来后仍带 `enc:v1:` 前缀"的台数 —— 即本机主密钥解不开（他机导出件），后端不静默清空，那就必须让人知道要重填。
3. `ServerList.handleImport`：选完文件先 `Modal.confirm`，用**当前真实数量**说明会替换掉多少台/多少条（并说明旧配置会进 `backups/`），确认按钮是 danger；取消 ⇒ 一次 `import_config` 都不发。结果分三条：台数为 0 ⇒ warning「文件里没有服务器，列表已清空」；正常 ⇒ success 带数量；有解不开的 ⇒ 额外 warning 点名台数与去处。
4. `mask_bearer_tokens` 改为 `lower: Vec<char>` + `to_ascii_lowercase()`（逐字符对齐，关键词是 ASCII 所以不损失判定力），关键词匹配抽成 `starts_at`。

### 证据

`tests/config-import.test.ts` **31 例**：store 层用假 `invoke` 验"汇总数量来自导入件、可用明文原样进 store、解不开的保留原值、前端不再补一次 `save_*`、`null` 导入件不炸"，`ServerList` 静态守卫验确认闸（含**闸门本身被删时必须红**的那一条）、danger 按钮、真实数量、空件不得报成功，以及跨语言守卫（`Ok(load_config())` 在、`Ok(parsed)` 不在、解析先于落盘、成功与失败都有审计、审计带台数、导出仍剔凭证）。Rust 新增 2 例：`import_returns_the_usable_view_and_never_wipes_on_error`（同一台机器导入自己的含凭证导出件 ⇒ 密码还原成明文可用、磁盘无明文、坏文件与缺失文件都报错且**现有配置一字未动**）、`bearer_masking_survives_multibyte_lines`（4 条含中文/emoji 的行必须不 panic 且仍打码，外加 ASCII 正例与 `Abearer ` 词边界负例）。

## 7.32 阶段五第二十五轮：进度条只说"传了多少"，卡住时屏幕上看起来一切正常（§7.27 遗留第 2 条）

### 这一轮查的是什么

§7.27 把进度改成后端真上报字节之后，横幅右侧只剩 `下载 1.4 MB / 42.9 MB`。两个看不出来的东西：

- **还要等多久**：45 MB 与 45 KB 传同样字节数时文案一模一样。
- **是不是卡住了**：后端 `should_emit_progress` 只在字节前进时发事件（250 ms 节流），传输停住 ⇒ 事件停 ⇒ **横幅完全静止**。静止的"1.4 MB / 42.9 MB"与"正在慢慢传"在屏幕上无法区分。

### 修法

`sftpTransfer.ts` 判定层加三个纯函数。时钟一律由调用方注入（函数自己不读 `Date.now()`），否则一次渲染里可能取到两个时刻，测试也无法确定：

| 函数 | 给不出值的条件（宁可不显示也不编） |
| --- | --- |
| `elapsedOf(t, now)` | 没起表时刻；时钟倒挂（`now < startedAt`） |
| `averageSpeedOf(t, now)` | 用时 ≤ 0；一个字节都还没过去 |
| `remainingOf(t, now)` | 算不出均速；总大小未知；已传完 |

- `beginTransfer` 多收 `startedAt`（面板传 `Date.now()`；非有限数字按"不知道"处理，绝不落成 `0`）；`settleTransfer` 多收 `now` 写 `endedAt` —— 完成/失败后显示整段用时，不再跟着墙钟继续涨。
- 文案：`下载 1.4 MB / 42.9 MB · 用时 3.2 s · 均速 381.5 KB/s · 约剩 1 分 52 秒`。三个措辞都是刻意的：**均速**（整段平均，含起表 IPC 往返与对端慢启动，不谎称瞬时）、**约剩**（由平均速度推出）、**大小未知时只给用时与均速，不给剩余**；一个字节都没过去时说「尚无数据」而不是 `0 B/s`。
- 卡住时"用时"必须还在走：`TransferBanner` 只在 `phase === "running"` 期间每 1 s 重渲染一次，结算即卸载定时器。定时器只当"重渲染把手"，显示值一律现取（§7.13 那批闭包读 useState 教训的反面用法）。

### 顺手抓到的一个真缺陷（浏览器实测）

第一版 `formatDuration` 是 `min = floor(ms/60000)` + `sec = round((ms%60000)/1000)`，实测横幅上出现过 **`约剩 14 分 60 秒`** —— 四舍五入进来的那 1 秒没进位到分钟。改成先 `round(ms/1000)` 得总秒数再拆，并把"任何时长都不得出现 `X 分 60 秒`"写进断言与 fuzz 不变量。

### 证据

## 7.35 阶段五第二十八轮：一批 7 个文件只说"这条传到一半"，既不知道是第几个也没地方喊停

### 这一轮查的是什么

§7.30 把批量下载改成"一次选目录 + 一条汇总"之后，剩下的两条都在 §7.27/§7.30 的遗留里：**整批串行、没有总进度、没有取消**。浏览器里看就是这样：选中 3 个文件点批量下载，屏幕上只有单条横幅在走，**不知道这是第几个、后面还有几个**；想停只能等它自己传完 —— 旧循环一路 `for` 到底，没有任何中断入口。

上传那条链上还有一个同源缺陷：`handleUpload` 对每个本地文件取 `basenameOf(localPath)` 当远端名，**两个不同目录下的同名文件（`~/a/x.txt` 与 `~/b/x.txt`）传进同一个远端目录时后一个直接覆盖前一个，而两条都报「上传成功」**。

### 修法

1. 新纯函数模块 `src/utils/sftpBatch.ts`：`beginBatch / startItem / finishItem / requestCancel / notStartedCount / describeBatch`。与判定层同一条规矩 —— **认不出就不显示**：`total <= 1` 时 `describeBatch` 返回 null（一条文件写"第 1/1 个"是噪声），一条都还没开始时说「准备中」而不是「第 0/3」，异常 `total`（0 / 负数 / NaN / Infinity / 小数）一律归一成非负整数。
2. 面板加整批横幅（在单条横幅之上，两层各说一件事）：`下载 3 个文件 · 第 1/3 · a.txt · 已结束 0/3`，右侧一颗「取消剩余 N 个」，只在还有没开始的条目时出现。取消**只挡还没开始的**：正在传的那条会传完 —— 后端没有中断单条传输的命令，假装能立刻停下就是骗人。
3. 循环里读的是 `batchRef.current`（实时），不是渲染快照的 state；`applyBatch` 同时写 ref 与 state，否则"按了取消"到下一轮判断之间会用到旧值。
4. 上传也走同一套：先 `planDownloads(basenames)` 做**净化 + 批内去重**（`x.txt` 与 `x.txt` → `x.txt` / `x (2).txt`，改过名写进汇总），远端落点用去重后的名字；单文件仍是一句式反馈（不给汇总、不给横幅），多文件才汇总。
5. `summarizeBatch` 加 `notStarted` 一档（「已取消 N 个（未开始）：…」，有它就不能算 success），并把改名的措辞从「因文件名不安全」改成不猜原因的「已改名以免互相覆盖」（下载侧是真不安全，上传侧是批内撞名）。

### 证据

`tests/sftp-batch.test.ts` **41 例**：状态机矩阵（准备中 / 第 N/M / 取消中 / 跑完不越界）、异常 `total` 五种归一、**2000 轮确定性交错**（随机 start/finish/cancel：`started ≤ total`、`finished ≤ started`、取消后不再开始新条目、`total<=1` 永不给文案、文案里不出 `NaN`/`undefined`，违例 **0**、取消分支实际命中 > 500 轮）、汇总四态（含"不传 `notStarted` 时与上一轮逐字相同"这条防回归）、面板接线静态守卫（两条批量路径都读 `cur?.cancelled`、取消按钮有 `aria-label` 且只在有余量时出现、整批横幅与单条横幅分开渲染、每条结束都推进 `finished`、上传走去重后的落点名、批量路径不再逐条弹成功）。

浏览器实测（真 `App` + 真 `SftpPanel`，`sftp_download` 的 resolve 握在探针手里，vite :8947，测完已停、`probe_tmp/` 已删）：

## 7.36 阶段五第二十九轮：整批只知道"第几条"不够 —— 加上整批字节、百分比与约剩

### 这一轮查的是什么

§7.35 的整批横幅落地后，遗留里自己写了一句：**"整批只反映第几条，没有整批字节数/总百分比"**。这一轮补上它 —— 30 MB 的 3 个文件和 30 KB 的 3 个文件，`第 2/3` 这一行看起来一模一样；而真正决定"还要等多久"的是字节，不是条目数。

顺带修掉同一条循环里的一个静默少做：批内某一项在点选之后被别的操作刷掉（列表刚刷新过）时，旧代码 `continue` 直接跳过，既不失败也不成功 —— 汇总里的数字对不上用户选中的个数，也没人解释少了哪个。

### 修法

`sftpBatch.ts` 的整批状态加字节维度，全部由调用方注入，模块自己不碰时钟、也不 import 传输状态：

| 字段/函数 | 规矩 |
| --- | --- |
| `bytesTotal` | 0 = **有任何一条大小未知** ⇒ 整批不给百分比与约剩。拿"知道的那几条"加总当总数，会画出一个偏小的假百分比 |
| `startItem(b, name, bytes)` | 每条开传时带上自己在列表里的 size；未知按 0 过账 |
| `batchBytesOf(b, live)` | 实时值只在"文件名 + 方向都对上、且还在传"时才计入，且**夹在本条大小之内**；对不上就少算一点，绝不多数 |
| `batchPaceOf(b, live, now)` | 用时为 0、一个字节没过、已传完 ⇒ 一律算不出（不给约剩） |
| `describeBatch(b, live, now)` | `… · 整批 15.0 MB / 30.0 MB · 50% · 约剩 19.0s`；大小未知时这三段一个字都不出 |

面板侧：整批文案要的实时值从既有的 `transfer` 状态映射（`filename`/`kind`/`running`/`transferred`），并给这一行也配一个秒级重渲染把手 —— 单条卡住时后端不再发事件，若整批行不自己走，它的"约剩"就会装作还在缩短。上传那条**不给整批百分比**：本地文件大小面板拿不到，不猜。

### 证据

`tests/sftp-batch.test.ts` **67 例**（上一口径 41）：字节维度矩阵（进出条目过账、`done` 越界夹取、文件名/方向/running 三种对不上分别忽略）、未知大小 ⇒ 文案里不出现「整批」、约剩的三种算不出、半批过账仍给约剩、整批传完不给约剩但仍报 100%，外加 **800 批随机大小 + 随机实时字节推进**的属性检查（百分比不越界、过账瞬间不塌陷、结束必到 100%、文案无 `NaN`/`undefined`，违例 **0**）。面板接线静态守卫：大小全已知才给 `bytesTotal`、每条带 `entry?.size`、实时值映射自 `transfer`、整批行有秒级把手、刷掉的条目记成失败而非静默跳过。
