## 3.2 PTY 后端与跨平台（重定向命题）

> **关键事实**：本项目无本地 PTY/本地 shell（[01 A-2](./01_现状审计与问题清单.md#a-2--不存在本地-pty--本地-shell与任务书假设不符需澄清)）。任务书中「PTY 后端与 macOS/Windows 差异」据实重定向如下。

### 真实跨平台差异点
| 维度 | macOS | Windows | 建议 |
|------|-------|---------|------|
| SSH 客户端 | russh（纯 Rust，平台无关） | 同左 | ✅ 无需平台分支，russh 已抹平 |
| 配置/日志目录 | `~/.z-terminal/`（[dirs::home_dir](../../src-tauri/src/config.rs)） | `%APPDATA%` 或 home | 统一用 `dirs` crate，避免硬编码 `/` |
| 文件打开 | `open`（[open_file_with_default_app](../../src-tauri/src/commands.rs#L691-L709)） | `explorer`/`start` | 用 `tauri-plugin-opener` 或按 `cfg(target_os)` 分支，且**加路径白名单**（见 [04](./04_数据安全与可靠性.md)） |
| 换行 | 远程 PTY 决定（`\r\n`） | 同左 | `convertEol` 需实测，见 3.4 |
| 文件权限 0600 | 支持 | 无 POSIX 权限 | 凭证加密（见 [04](./04_数据安全与可靠性.md)），不能只靠 chmod |

### 是否引入本地终端后端？
- **建议：暂不引入**（列为阶段五可选）。当前产品定位是远程 SSH 管理器，引入本地 PTY（如 `portable-pty`）会显著扩大安全面与维护成本。若产品确需，再单独立项，届时才涉及真正的 conpty/pty 跨平台。

## 3.3 并发模型与会话隔离（P0-3 核心改造）

### 问题
全局单 `Mutex<HashMap>` 在 `ssh_execute`/`ssh_pty_write`/`ssh_get_server_info` 中**跨 `await` 持锁**（[01 C-1](./01_现状审计与问题清单.md#c-1--全局-sessions-单-mutex-跨-await-持锁队头阻塞)）。任一长命令（或 `top -bn2 -d1` 采样）期间，全部标签键入/SFTP/诊断被阻塞，直接违反 P-3。

### 推荐方案（明确）
1. **锁粒度下沉**：全局 map 仅用 `RwLock<HashMap<String, Arc<Session>>>` 做「查表」，取出 `Arc<Session>` 后**立即释放全局锁**，后续 `await` 只持有该会话自己的锁。
   ```rust
   // 伪代码（规划，不在本方案实现）
   let sess = { sessions().read().await.get(&id).cloned() }; // 短暂读锁
   let sess = sess.ok_or("会话不存在")?;
   sess.execute(...).await?; // 不再持全局锁
   ```
2. **Session 内部字段已用独立 `Arc<Mutex<...>>`**（[SshSession 结构](../../src-tauri/src/ssh.rs#L26-L47)：handle/pty_writer/log_file 各自一把锁），改造成本低——只需保证 commands.rs 不再「外层全局锁 + 内层 await」。
3. **PTY 写入走 mpsc channel**（已有 [pty_writer: Sender<String>](../../src-tauri/src/ssh.rs#L36)，容量 256）：`ssh_pty_write` 只需 `tx.send().await`，不应持全局锁。
4. **execute（非交互命令）**：为每会话提供独立的 exec channel，避免与 PTY 读循环争锁；输出累积加上限（见 3.5）。

### 契约建议
- `ssh_execute` / `ssh_pty_write` / `ssh_get_server_info` 全部改为「先克隆 `Arc<Session>`、释放全局锁、再 await」。
- 验收：单会话跑 `sleep 30` 期间，其它会话键入到回显延迟 < 50ms（见 [06](./06_测试验收与风险清单.md)）。

## 3.4 渲染性能、背压与高频输出（P1）

### 问题链
后端每收到一个 `ChannelMsg::Data` 就 `app.emit` 一次 **且** 同步 `write_log`（[ssh.rs PTY 循环](../../src-tauri/src/ssh.rs#L537-L609)、[write_log](../../src-tauri/src/ssh.rs#L614-L625)）；前端每事件 `term.write`（[TerminalView](../../src/components/TerminalView.tsx#L253)）。高频输出下：IPC 洪泛 + 磁盘锁竞争 + 渲染抖动。

### 推荐方案（明确，三层）
1. **后端批处理**：PTY 读循环用「时间窗 + 字节阈值」合并输出再 emit。
   - 规划参数：16ms 窗口 **或** 累积 ≥ 64KB 立即 flush（取先到者）。
   - 目标：IPC 事件数较现状下降 ≥ 80%（`cat` 100MB 场景，见 [00 0.7](./00_总览与优化优先级.md#07-量化验收目标摘要完整-12-项见-06)）。
2. **日志移出热路径**：`write_log` 改为独立 task + channel，PTY 循环只 `try_send`，日志按行/按块异步落盘；避免每块 lock+格式化时间戳。日志须脱敏且可关闭（见 [04](./04_数据安全与可靠性.md)）。
3. **前端背压**：`term.write(data, callback)` 配合「未确认写入计数」，超过阈值暂缓消费下一批（xterm 内部已有缓冲，避免无界堆积）。
4. **渲染加速**：评估 `@xterm/addon-webgl`（规划新增依赖），初始化失败回退 canvas/DOM。

### convertEol 复核（🟡 待验证）
- 现状 `convertEol:true`（[TerminalView](../../src/components/TerminalView.tsx#L189)），远程 PTY 通常已输出 `\r\n`，可能重复处理（[01 C-6](./01_现状审计与问题清单.md#c-6--convertEol-与-pty-输出可能重复处理换行)）。建议在隔离环境实测后决定是否关闭。

### O(N) 扇出优化（P2）
- 现状每 pane 各注册一个全局 `pty-output` 监听再按 session_id 过滤（[01 C-4](./01_现状审计与问题清单.md#c-4--每个-pane-各注册一个全局-pty-output-监听on-扇出)）。建议改为**单一分发器**：前端一个全局监听，按 `session_id` 路由到对应 pane 的 write，避免 N 份重复接收。

## 3.5 execute 输出无上限（P1）

- 问题：[execute](../../src-tauri/src/ssh.rs#L283-L310) 把所有 Data push 进单个 String，无上限、无超时（[01 C-5](./01_现状审计与问题清单.md#c-5--execute-输出无上限累积在内存)）。`cat /dev/urandom` 会 OOM，叠加全局锁 → 冻结全应用。
- 推荐：
  - 输出上限（如 10MB）截断并标记 `truncated:true`。
  - 执行超时（如 60s，可配），超时中止 channel。
  - 契约：`ExecResult` 增加 `truncated`/`timed_out` 字段（[types/index.ts ExecResult](../../src/types/index.ts#L75-L80) 规划扩展）。

| 连接超时不取消底层 | [connectToServer Promise.race](../../src/stores/serverStore.ts#L159-L207)、[01 F-3](./01_现状审计与问题清单.md#f-3--连接超时用-promiserace未取消底层-rust-连接) | 后端 connect 支持取消 token；前端 clear timer，超时后调 disconnect 清理 |

### 资源回收契约
- `disconnect` 应保证：abort 所有 forwards、关闭 log task、drop channel、从全局 map 移除，且**幂等**（重复调用不 panic）。
